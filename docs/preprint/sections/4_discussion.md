# 4 Discussion

## 4.1 Provenance Held but Left the Free Choices Open

The harness answered the first question in the way it was designed to. Small language models built, checked and ran models of heat, flow, deformation and transport from requests in English and Korean, refused most of what the verification does not cover, and quoted only numbers that could be traced to the card, the model inputs or the request: in all 16 runs with the OpenAI models and in all 21 stand-in runs, including the one that failed its scenario for another reason. This is a property of the harness rather than of the models. The language model cannot write simulator input, cannot run a configuration whose verification has not passed, and, in the agent built on the Agents SDK, cannot show the user a number that the output guardrail cannot trace; apart from defects in the harness or the simulator, what it can still do wrong is limited to the choices the harness leaves open.

The point-heat-source scenario shows what those choices cost. Two answers with flawless provenance, from two models, were wrong by 34 % and 152 %, because both models coarsened a mesh that the example had set correctly, one at the source only and the other also around it. Neither the judge nor the guardrail could see it, because both check how a number was obtained and not whether the model that produced it resolves the physics. FEABench met the same gap from the other side, when an exported default temperature passed its judge (Mudur et al., 2025), and JutulGPT observed that choices left to simulator defaults never enter its record of assumptions (Lie et al., 2026). In our harness the default was right and the language model's deliberate change was wrong, which makes the gap harder to see: the mesh appeared in the model tree, passed every quality check, and was reported on the results page.

The harness also gave one model the evidence it needed. gpt-6.1-terra ran the half-element-size comparison, saw its value change by 0.257 MPa, said so, and still reported the coarse value as the answer. A tool that reveals a problem therefore does not by itself prevent the answer the problem spoils. A check acts on the evidence, for example by refusing the mesh, or by a rule, not yet in the harness, that turns a large change under refinement into a warning on the card that the answer must report.

The remedy that worked in the reruns was such a check, tied to the physics of the configuration rather than to the procedure. The source-resolution rule compares the element at the source with the distance heat has spread by the first output, a length the user never states and neither model considered. With the rule at ℓ/2, the gross errors disappeared but one answer was still 8 % low; at ℓ/4, the model that had its mesh refused took the suggested size, refined the far field as well, and came within 0.5 % of the exact solution. The sweep shows that ℓ/4 itself leaves an error of about 6 % with the example's far field, so the released rule refuses elements larger than ℓ/8, the coarsest size within the 3 % tolerance of the verification case. A threshold set this way ties the rule to the accuracy the verification established, but we set it from one example and one probe point, and it refuses meshes that may be adequate for quantities far from the source.

## 4.2 Finding the Answers That Lack a Check

The wrong answers were found by recomputing every answer card on the reference mesh of the example it started from. This audit is cheap, because it reuses the language model's own model tree and card items and changes only the mesh, and it needs no exact solution. It does rely on the mesh of the starting example. For the point-heat-source example this is the mesh of the verification case; for the other examples it is a mesh we chose. Its limits are as clear as its use. It detects answers that depend on a discretization choice. In our runs it singled out the one scenario, among the {{mesh_changed}} runs with a changed mesh, in which the change altered a reported value by more than a few per cent; all other recomputed card values agreed with the reference mesh within {{audit_other_max_pct}} %, and {{audit_other_within_02}} of {{audit_other_n}} within 0.2 %. It cannot detect an answer that solves a different problem from the one asked. The stand-in model's steady-state answer would not have been exposed by recomputing it on another mesh. Its error lies in calling a transient result steady without showing that it had stopped changing, not in the mesh. Interpretation errors of this kind need a different check: the harness refused steady transport, but nothing stopped the model from running the transient model instead and calling its final state steady.

These results suggest a hypothesis that further tests can falsify: in agents that run verified simulators through constrained tools, wrong answers will concentrate in the choices the harness leaves to the language model (element size, time steps, output times and the reading of the request), and they will pass checks of procedure and provenance. If the hypothesis holds, the work of making such an agent reliable shifts from the language model to the harness, which should attach a physics-based check to each free choice. Recomputing answers on the meshes of their starting examples is then a practical way to find the choices that still lack one, best with meshes that a verification case has checked, as the point-source mesh was. Our evidence for it is narrow: one scenario with a discretization error, one with an interpretation error, and a small number of runs.

## 4.3 Limitations

The tests are small. Each scenario ran once per model, so we report outcomes, not rates, and the 16 API runs and 21 stand-in runs cover 8 and 21 requests chosen by us, most of them starting from an example. The judge, the guardrail and the scenarios are ours, and two faults of the guardrail were found and fixed while preparing this paper: it did not read numbers written directly before Korean characters as numbers of the request, and it did not accept step counts reported on the card. The first sent two first answers of the API runs back for a rewrite (Section 3.2); the stand-in results are scored with the released guardrail. The source-element sweep covers one example, one probe point and one time. All results were computed on macOS; on Linux x86_64 we could test only under emulation, where OpenGeoSys returned zero temperatures on triangular elements, so the harness runs a small test problem before the first triangular mesh on each computer and refuses triangles where it fails. Version 0.1 covers twelve configurations of two-dimensional, axisymmetric and simple three-dimensional problems; reactive chemistry, unsaturated and two-phase flow, bentonite swelling, fractures, plasticity and three-dimensional mechanics are outside it, and its results are meant for learning and first estimates, not for design, licensing or safety assessments.

# 5 Conclusions

An agent harness for OpenGeoSys that gives the language model only the modeling choices, computes only configurations whose verification passed, and checks the numbers in the answer against the run, the inputs and the request let two small OpenAI models and a stand-in model carry requests in heat, flow, deformation and transport through to answers whose checked numbers could all be traced. Traced numbers did not make the answers correct. In the one scenario where both OpenAI models coarsened the mesh at a point heat source, gpt-6-luna also around it, their pore-pressure rises were −0.507 and 0.635 MPa against 0.967 MPa. One model had seen the sensitivity in its own comparison and reported the value anyway, and only a recomputation on the example's reference mesh exposed both errors. A resolution rule tied to the heat-spread length removed the gross errors, and the released rule refuses elements larger than one eighth of that length, for which the example's error at the probe is within the 3 % tolerance of its verification case. For agents that run simulators, we propose to treat every choice left to the language model as a place where a physics-based check is needed, and to audit answers by recomputing them on reference meshes, preferably ones checked against verification cases, while remembering that such an audit cannot catch an answer to the wrong question.
